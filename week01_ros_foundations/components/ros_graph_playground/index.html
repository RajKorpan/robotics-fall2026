Part 3: Your first introduction to ROS 2

ROS 2 connects the pieces of a robot

ROS 2 stands for Robot Operating System 2, but it is not an operating system like Windows, macOS, or Linux. It is a robotics middleware framework: libraries, conventions, and tools that let independently running robot programs discover one another, exchange structured data, and be inspected as one system.

What ROS 2 is

A shared communication framework for modular robot software

A mobile robot may use separate programs for a camera, LiDAR, teleoperation, obstacle avoidance, mapping, planning, motor control, simulation, and visualization. ROS 2 supplies common ways for those programs to communicate. This lets developers replace or debug one component without rewriting the entire robot.

Middleware sits between your programs and the underlying computer network. Your programs describe what information they produce or need. ROS 2 handles discovery and transports that information between compatible components, whether they run in one process, several processes, or on several computers.
CommunicationNamed interfaces for streams, requests, responses, and actions.
Development toolsCommands for building, launching, inspecting, recording, and debugging.

ROS 2 does not decide what your robot should do. Your code and the packages you choose provide perception, planning, and control. ROS 2 provides the structure and communication that allow those components to work together.

Example 2

Topic stream versus service request

A topic is useful when new information keeps arriving, such as LiDAR measurements. A service is useful when a client needs one operation performed and expects one response, such as resetting a simulation.

Topic: ongoing publish and subscribe communication. Service: one client request and one server response.

What to do

  1. Run the LiDAR topic and watch several measurements arrive over time.
  2. Call the reset service and watch one request travel to the server and one response return.
  3. Watch the robot return to its starting position when the service runs.

Example 3

A broken connection changes robot behavior

The robot’s safety behavior depends on a complete Sense, Decide, Act path. Different failures affect different parts of the system. Closing a visualization is not the same as losing the sensor data used for control.

Fail safe: move to a safer state, such as stopping, when required information is missing or invalid.

Example 4

ROS 2 tools answer specific debugging questions

The command line lets you inspect the live ROS graph instead of guessing. Each command answers a different question about programs, interfaces, connections, or data.

Inspect before changing: first determine what is running and how it is connected. Then form a specific explanation for the failure.

Inspection checklist

What to watchThe graph can still contain a topic name even when its publisher count is zero. Inspect connections and data, not only names.

What to carry into the ROS simulation

  • The robot is a system of independently running nodes.
  • Topics carry typed message streams from publishers to subscribers.
  • Services perform discrete request-response operations.
  • A visible interface does not prove that publishers, subscribers, and types are correct.
  • ROS 2 inspection tools let you observe the implemented architecture before modifying it.
